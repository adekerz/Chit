# Chit — контекст для продолжения разработки

Личный цифровой блокнот официанта. Не связан с iiko API — все отметки
(«пробито», «отдано», «пречек») ставит сам официант вручную; это внутренняя
замена бумажным чекам, не интеграция с POS.

Стек: один файл `index.html` (vanilla JS, без сборки, без зависимостей),
`manifest.json` + `sw.js` для PWA. Осознанно без фреймворка — ставился приоритет
на «быстро запустить и проверить в реальной смене», а не на архитектуру про запас.

## Почему так, а не иначе (решения, которые не стоит откатывать не подумав)

- **Без API iiko принципиально.** У ресторана нет доступа к API. Значит двойной
  ввод (блокнот → потом руками в айку) — это постоянная плата, а не временный
  компромисс. Из этого следует главный критерий качества: скорость ввода важнее
  любой фичи. Если новая фича замедляет тап-путь до добавления блюда — она того
  не стоит.

- **Кнопка «Пробить всё» на уровне стола, а не пробитие по одной позиции.**
  Официант пробивает заказ в айке целиком одним походом к терминалу, не бегает
  после каждого блюда. Одна кнопка — один таймстамп на все непробитые позиции.
  Точечное «П» на позиции оставлено для случаев дозаказа/довозки после основного
  пробития.

- **Хранение данных: `window.storage` (Claude-артефакт) с фолбэком на
  `localStorage` (реальный хостинг).** См. функцию `store` в начале `<script>`.
  На Vercel работает только localStorage-ветка — значит данные живут в браузере
  конкретного телефона, без синка между устройствами. iOS может почистить
  localStorage у сайтов без активности ~7 дней; установка на домашний экран
  снижает риск, но не убирает.

- **Пуш-уведомления о готовности — с жёстким ограничением iOS.** Пока PWA открыт
  на экране — звук/вибро/баннер срабатывают точно по таймеру. При заблокированном
  экране iOS останавливает JS, поэтому таймер не «выстрелит» сам — сигнал придёт
  при следующем открытии приложения (см. `checkReady()` + слушатель
  `visibilitychange`). Обойти без своего Web Push сервера нельзя — это платформенное
  ограничение, не баг кода. Не тратить время на попытки «починить» это без бэкенда.

- **Время готовки (`~минуты` в формате меню) может переопределяться вариантом
  модификатора** (`rare~12` vs `well done~22`) — см. `cookMinutes()`. Базовое
  время у блюда — дефолт, если модификатор не выбран или у него нет своего `~`.

- **Стоп-листы не автоматические.** Официант выставляет их вручную в начале
  смены на отдельном экране (`renderStop`). Никакой синхронизации с кухней нет
  и не планировалась — попытки её добавить без API бессмысленны.

## Формат данных меню/зала — текстовый DSL, не JSON

Парсится функциями `parseMenu()` / `parseTables()`. Формат специально сделан
человекочитаемым для правки прямо в текстовом поле настроек на телефоне, без
JSON-редактора. Если будешь усложнять формат — сохраняй readability, это фича,
не долг.

## Что ещё не проверено в реальной смене (открытые вопросы)

- Времена готовки в демо-меню — не настоящие, ставились «от балды». Если на
  практике сигнал будет систематически приходить раньше/позже реальной
  готовности — обсуждалась идея глобального коэффициента (например ×1.3 в
  запар), а не правка каждого блюда вручную.
- Не проверено, устраивает ли скорость навигации по иерархии меню по сравнению
  с поиском — если поиск окажется быстрее, стоит сделать его стартовым экраном
  меню с автофокусом клавиатуры, а дерево категорий убрать во вторую очередь.
- Название приложения — **Chit** (талон заказа на кухню), выбрано за точность
  термина и краткость под иконкой. Не переименовывать не глядя в код: `manifest.json`
  и `<title>`/`apple-mobile-web-app-title` в `index.html` должны совпадать.

## Обновление: аллергены, вино, объёмы, сервисный сбор (реальное меню KÖK)

Меню/бар/вино заменены на реальные данные ресторана из PDF (`Main menu`, `Bar menu`,
`Breakfast menu`, `Wine card`) и `Пособие для официантов.xlsx`. Дизайн-PDF читались
рендером страниц в изображения (pdftotext/pypdf давали перемешанный текст из-за
многоколоночной вёрстки) — цены и составы сверены визуально.

### Новые токены DSL блюда (после цены, порядок любой, различаются по первому символу)
`Название | цена | ~время | !обяз | ?необяз | @аллергены | $вино`
- `@аллерген, аллерген` → массив `d.allergens`. Источник — колонка «Аллергены» в
  Пособии (авторитет), НЕ угадывание по ингредиентам.
- `$текст` → строка `d.wine` (одна строка «что предложить»). Для кухни это бокальное
  вино из «По бокалам» Пособия = первая страница Wine card (Wines by Glass).
- Вариант модификатора теперь `label~время~цена` — цена варианта переопределяет базовую
  (см. `dishPrice()`), используется для объёмов бара (San Pellegrino 0.25/0.75,
  разливное пиво 0.35/0.5). База таких позиций `| 0 |`, объём — обязательный модификатор.

### Поиск
`matches()` — тонкая обёртка над `textMatch(n,q)`. Добавлен `matchesAllergen(dish,q)`:
поиск по `dish.allergens` тем же алгоритмом. В меню и стоп-листе фильтр
`matches(d.name,q) || matchesAllergen(d,q)` — «кунжут» находит блюда, где кунжут аллерген.

### Сервисный сбор
`S.serviceFee` (%, по умолчанию 10, редактируется в настройках рядом с порогом «висит долго»).
`subtotal()` — сумма позиций, `serviceAmount()` — сбор, `total()` = подытог + сбор.
В счёте стола и при закрытии сбор показан отдельной строкой (не спрятан внутри итога).

### Экран-справочник бутылочного вина
`WINE_CARD` (текстовый DSL, `parseWine()`) + `renderWine()`, кнопка «Вино» на экране зала.
~90 бутылок по цвету/стране/сорту с поиском (`textMatch` по названию/стране/сорту).
Справочник отдельный, в объект блюда не встраивается.

### Важно про данные
`DEFAULT_MENU` применяется только при ПУСТОМ хранилище. Если на устройстве уже сохранено
старое меню (`floor-v2` в localStorage), новое дефолтное меню не подхватится само —
нужно вставить его текст в Настройки → Меню (или очистить localStorage). Аллергены из
Пособия перед реальной сменой стоит перепроверить глазами — это зона безопасности.
